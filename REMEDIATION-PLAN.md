# Rencana remediasi CI/CD dan deployment KostKita

Tanggal: 3 November 2026, diperbarui setelah remediasi lokal. Perubahan ada pada branch `codex/cicd-production-remediation` dan belum dipush. Prioritas yang memerlukan host apply hanya setelah inventaris read-only; tidak ada runtime production yang diubah. Tetap gunakan build Docker Compose lokal pada target LXC aplikasi, tanpa GHCR atau registry image aplikasi. Lihat [CICD-AUDIT.md](CICD-AUDIT.md), [PROXMOX-DEPLOYMENT-AUDIT.md](PROXMOX-DEPLOYMENT-AUDIT.md), dan [Infrastructure Verification Report](INFRASTRUCTURE-VERIFICATION-REPORT.md) untuk bukti dan blocker.

## 0. Selesaikan bukti sebelum memilih perubahan

1. Dari akses Proxmox read-only, cocokkan node, `pct config 10026`, hostname dan IP di dalam LXC. Dari GitHub Actions dan service runner, cocokkan runner ID/group/labels, UID, service, workspace dan execution host; catat juga direktori dan hak pengguna. Jangan menyimpulkan lokasi dari label. **Selesai:** identitas dan perbedaan dari dokumen terbukti dengan waktu/sumber; bila akses tidak tersedia, tetap tandai belum terverifikasi.
2. Periksa riwayat dua workflow: event, conclusion, tested SHA, deploy SHA, ref, runner, waktu dan log yang disanitasi; cek izin dispatch, branch protection, environment protection, policy Actions dan concurrency. Bandingkan urutan deploy dengan urutan commit. **Selesai:** contoh push dan dispatch dapat ditelusuri dari test sampai runtime, atau kesenjangan dicatat.
3. Identifikasi runtime, versi Docker/Compose atau alternatif yang benar-benar berjalan, port dan image ID, status proses, storage, owner/mode dan keberadaan env tanpa menampilkan nilainya. Jika ada checkout Git di target, secara read-only periksa branch, remote yang sudah disanitasi, SHA, modifikasi, konflik, permission dan `safe.directory`; workflow yang diperiksa sendiri memakai rsync, bukan git pull. Periksa disk, inode, RAM/swap, CPU/cgroup dan beban produksi; gunakan metrik atau log historis untuk durasi dan konsumsi build jika tersedia, tanpa memulai build saat audit. **Selesai:** kapasitas, baseline dan source of truth terdokumentasi tanpa kredensial.
4. Periksa ingress aktual pada Cloudflare dan Traefik, host/port/protokol, aturan trusted proxy serta listener LXC; uji jalur end-to-end, HTTPS dan aset. Periksa service, scheduler, queue jika digunakan, koneksi database, migrasi pending, log tersanitasi dan backup off-host/hasil restore. **Selesai:** tiap klaim memiliki bukti live atau status belum terverifikasi; tidak ada token/log sensitif disalin.

## 1. P0 — proteksi deployment dan data

- Batasi deployment otomatis ke run `tests` yang sukses untuk **push `main` dari repository tepercaya**, dengan verifikasi bahwa checkout, test dan kandidat memiliki SHA yang sama. Batasi dispatch ke ref/aktor tepercaya dan wajibkan hasil CI untuk SHA tersebut, atau nonaktifkan dispatch sampai jalur aman tersedia. Gunakan protection environment dan branch sesuai hak yang telah diverifikasi; runner deployment hanya mengeksekusi kode tepercaya. **Selesai:** uji push valid, test gagal, PR/head `main`, fork, dispatch ref lain dan SHA berbeda; hanya kasus yang diizinkan dapat menuju produksi.
- Gunakan satu concurrency group tetap untuk target produksi, dan lock host yang mencakup seluruh aktor deployment termasuk operator manual; tetapkan kebijakan antrian/coalescing. Sebelum aktivasi, cek kandidat masih memenuhi kebijakan urutan terhadap `main` dan release aktif; jangan biarkan run lama menimpa release baru. **Selesai:** simulasi run paralel/ref berbeda, CI selesai terbalik, dan interupsi tidak menghasilkan dua aktivasi atau regresi SHA.
- Siapkan backup konsisten PostgreSQL dan file persisten di luar node, beserta APP_KEY di penyimpanan aman; uji restore terisolasi dan catat RPO/RTO. Kaji tiap migrasi terhadap app lama dan baru, termasuk locks dan durasi; gunakan expand/contract, dan rencanakan pemulihan maju jika diperlukan. Jangan otomatis menjalankan `migrate:rollback`. **Selesai:** restore rehearsal terbukti dan migrasi kandidat memiliki rencana kompatibilitas/pemulihan tertulis.

## 2. P1 — release dapat diidentifikasi dan dipulihkan

1. Pada runtime yang terbukti, bangun kandidat terisolasi menggunakan source SHA persis, dependency lockfiles dan konfigurasi produksi yang tepat; jangan memutasi direktori/source aktif. Untuk Compose yang ada, pertimbangkan tag image immutable berbasis SHA untuk **seluruh** service, disertai digest base/dependency, manifest release dan penyimpanan image lama. Struktur direktori releases/current adalah alternatif bila sesuai; symlink saja tidak membuat pergantian banyak container atomik. **Selesai:** dua kandidat dan release aktif dapat dibedakan secara andal dan diuji tanpa mengganti yang aktif.
2. Tentukan prosedur aktivasi terkoordinasi app/web/scheduler sesuai runtime, dengan shared env/storage terpisah, lock, izin minimal dan transisi trafik yang diuji. Jika zero downtime tidak layak pada kapasitas ini, nyatakan jendela gangguan yang diterima dan rencana recovery. Pastikan file `src/.env` lama tidak override file produksi secara tidak sengaja setelah memeriksa keadaan aktual. **Selesai:** uji interupsi saat sync, build, migrasi, pergantian setiap service dan health; state diketahui dan dapat dipulihkan.
3. Simpan release/image terakhir yang diketahui baik beserta SHA dan kompatibilitas schema; definisikan rollback kode/config/traffic yang eksplisit, bukan rollback database otomatis. Uji saat aset, layanan, atau migrasi gagal, termasuk hilangnya proses deploy dan prune. Lindungi release yang dibutuhkan dari garbage collection. **Selesai:** latihan rollback dengan data uji membuktikan versi aktif, integritas data dan target waktu pemulihan.
4. Kunci atau catat digest base image dan toolchain; jalankan build production image serta acceptance PostgreSQL pada lingkungan uji yang setara. Tetapkan batas build sesuai pengukuran, timeout readiness DB, disk/inode minimum dan rencana penanganan resource. **Selesai:** kegagalan/kehabisan resource tidak mengganti release aktif dan hasil build dapat ditelusuri.

## 3. P1 — status deployment yang bermakna

- Tambahkan readiness terikat kandidat: proses/service sehat, Laravel boot, database dapat diakses dan schema sesuai, app/web/scheduler memakai release yang diharapkan, manifest dan minimal satu asset hash berhasil diambil, serta jalur ingress publik bekerja jika sudah diaktifkan. Jangan mengandalkan HTTP `/up` atau `migrate:status` saja. **Selesai:** pengujian fault injection untuk setiap pemeriksaan menghasilkan status gagal, diagnosis aman dan pemulihan sesuai runbook.
- Periksa bahwa scheduler berjalan dan tugas berakhir dengan sukses; bila aplikasi benar-benar memakai queue, deploy dan periksa worker yang memuat kode release yang benar dan restart secara aman. Sanitasi logs, jangan tampilkan environment, token atau konfigurasi Compose terinterpolasi di CI. **Selesai:** kegagalan scheduler/worker terdeteksi, tanpa kebocoran secret di log.
- Audit build dan health log, dan hapus/ubah prune global hanya setelah retensi disepakati. Jelaskan hubungan antara health gate, langkah housekeeping dan status akhir. **Selesai:** sukses berarti kandidat aktif dan semua pemeriksaan wajib lolos; kegagalan pasca-aktivasi menunjukkan keadaan yang sebenarnya.

## 4. P2 — sinkronkan dokumentasi setelah verifikasi

Perbarui [DEPLOYMENT-GUIDE.md](docs/deployment/DEPLOYMENT-GUIDE.md), [ADR-004](docs/decisions/ADR-004-proxmox-docker-deployment.md) dan [HOMELAB-SSOT.md](docs/deployment/HOMELAB-SSOT.md) berdasarkan bukti live, termasuk status artifact yang kini sudah ada di repository, port yang diputuskan, identitas target, runtime, ingress, release, backup dan tanggung jawab operasional. Pisahkan status target, owner-reported dan observasi bertanggal. **Selesai:** dokumen tidak saling bertentangan dan tidak mengklaim instalasi/go-live yang belum dibuktikan.

## Impact assessment dan gerbang persetujuan produksi

**Keadaan sekarang: BLOCKED.** Tidak ada jaminan tanpa downtime: Compose mengganti app, web dan scheduler satu per satu, dan health gagal setelah aktivasi dapat meninggalkan layanan parsial. Build lokal bersaing dengan layanan untuk CPU, RAM dan disk; skrip kini gagal tertutup tanpa ambang disk/inode yang diukur, tetapi RAM/CPU dan retensi release belum ditentukan. Entrypoint kini fail-closed tanpa mengubah permission storage secara rekursif. Pending migrations menghentikan deployment; kompatibilitas migration production belum diketahui. Catat window layanan, kapasitas terukur, pemilik tindakan, dan ambang pembatalan sebelum meminta persetujuan.

1. **Read-only:** cocokkan runner dan LXC dengan node, IP, user, direktori, Docker project/network/volumes, environment protection, listener dan ingress. Catat SHA dan image ID aktif, permission storage dan kapasitas; jangan tampilkan rahasia. Jika berbeda dari target yang ditetapkan, hentikan dan laporkan mismatch.
2. **Persiapan backup dan recovery:** identifikasi backup PostgreSQL yang konsisten, storage privat dan APP_KEY terenkripsi di luar node; buktikan restore pada lingkungan terisolasi dan catat RPO/RTO. Simpan image/tag, konfigurasi dan SHA release terakhir yang diketahui baik. Periksa kompatibilitas schema dua arah dan strategi expand/contract. `migrate:status` tidak memvalidasi checksum isi file; migration `2026_11_03_000022` berubah pada riwayat repository (`15e70ef`) sehingga cocokkan schema dan migration history aktual. Jangan asumsi rollback kode aman setelah perubahan schema.
3. **Perubahan live yang memerlukan persetujuan terpisah:** perbaikan identitas/runner/ingress/permission, penyediaan proteksi GitHub dan operational switch, migrasi database, restart/aktivasi service, serta pengaktifan workflow baru. Pisahkan izin migrasi dari izin aktivasi dan jelaskan dampak masing-masing. Backup/restore evidence saat ini merupakan gerbang operasional yang harus ditinjau oleh pemilik; repository belum memiliki sumber bukti backup yang bisa diverifikasi otomatis.
4. **Eksekusi setelah izin:** pada window yang disetujui, jalankan kandidat yang lolos CI dengan SHA sesuai `main`, pastikan backup dan pemeriksaan pra-aktivasi berhasil, lalu aktivasi dan uji layanan, SHA app/web, schema, aset, scheduler dan ingress. Pending migration menghentikan skrip; rencanakan migrasi kompatibel sebagai tindakan tersendiri.
5. **Kegagalan dan pemulihan:** hentikan aktivasi tambahan, catat image dan schema yang benar-benar aktif dan amankan trafik sesuai runbook. Jika kompatibilitas data telah dibuktikan, operator dapat mengembalikan app/web/scheduler ke image dan konfigurasi release terakhir yang diketahui baik melalui prosedur yang diuji; bila tidak, gunakan perbaikan maju atau restore yang telah disetujui. Jangan jalankan `migrate:rollback`, hapus volume, atau restore data secara otomatis. Catat hasil health dan waktu pemulihan sebelum menyatakan sukses.

**Batas runtime tambahan:** konfigurasi Inertia mengaktifkan SSR, tetapi Compose saat ini tidak mendefinisikan service SSR/Node. Perilaku SSR aktual belum diuji; validasi bersama inventory runtime sebelum aktivasi.

**Risiko dependency lokal:** `npm audit` melaporkan 2 temuan low (`deepmerge` transitif dan `@sveltejs/vite-plugin-svelte`), tanpa perbaikan yang ditawarkan saat pemeriksaan. Advisory: [GHSA-gcqx-w48m-w2h4](https://github.com/advisories/GHSA-gcqx-w48m-w2h4). Tinjau kembali saat update dependency; jangan mengklaim bebas kerentanan.
