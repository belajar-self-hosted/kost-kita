## Production impact and go/no-go conditions

- Compose replacement is not an atomic switch; app, web and scheduler can be on mixed versions during failure. Downtime cannot be estimated until runtime, capacity and activation sequence are observed and rehearsed.
- Production database migration compatibility is unknown. The revised local deployment script aborts on pending migration status and does not execute migrations or database rollback. Migration is a separate approval/action.
- Backup presence is not restore evidence. No production action is acceptable until isolated restore success, RPO/RTO, scope and a known-good previous release are documented.
- After any future approved activation, verify expected SHA for app/web/scheduler, Laravel boot, database/schema, Vite asset hash, `/up`, public ingress, and scheduler/queue operation. Failed health means failed release; recovery steps must use a rehearsed previous release or approved forward-fix/restore.
- **Go only when:** current workflow/run state is controlled; repository protections and least privilege are verified; runner is proven on the exact target LXC; runtime identity and capacity match; DB and backup/restore gates pass; ingress and release SHA are verified; automated checks pass; rollback is rehearsed; and the owner gives separate explicit approval for any production push/workflow activation/deployment/migration.
