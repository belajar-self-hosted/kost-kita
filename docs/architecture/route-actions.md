# Kontrak Route dan Action

## Tujuan dan batas

Dokumen ini menetapkan kontrak HTTP untuk implementasi MVP Laravel + Inertia + Svelte. Route web mengirim halaman Inertia dan form biasa berbasis session; MVP tidak menyediakan API JSON terpisah untuk UI, login penyewa, atau route staf. Kontrak ini memakai aturan bisnis pada dokumen terkait dan istilah/entitas pada [Model Data](../data/model.md) serta [Skema Relasional](../data/relational-schema.md). Nama tabel atau kolom fisik mengikuti skema relasional, bukan ditentukan ulang di sini.

Gunakan route name Laravel yang konsisten dengan nama handler/action pada tabel. Action yang mengubah status bisnis memiliki endpoint eksplisit; jangan menerima `status`, `tenant_id`, `owner_id`, nilai saldo, atau hasil kalkulasi dari klien sebagai perintah bebas.

## Aturan global

### Autentikasi dan scope

- Route publik terbatas pada registrasi Pemilik Kost, login, verifikasi email, pemulihan/reset kata sandi, serta halaman informasi yang memang diperlukan autentikasi.
- Route `/owner/*` memerlukan session terautentikasi, email terverifikasi, role Pemilik Kost, dan akun aktif.
- Route `/platform/*` memerlukan session terautentikasi, email terverifikasi, role Super Admin, dan akun aktif.
- Tidak ada registrasi Super Admin publik. Pembuatan akun Super Admin mengikuti prosedur administrasi platform yang dibatasi.
- Pemilik hanya mengakses resource pada tenant miliknya. Backend memperoleh tenant dari user terautentikasi, lalu memakainya pada query, policy, route model binding, write, audit, dan export. Filter `property_id`, `room_id`, atau ID lain dari request harus discope ulang ke tenant tersebut.
- Jangan pernah menerima `tenant_id`/`owner_id` dari form sebagai bukti kepemilikan. Super Admin memakai policy platform eksplisit; route platform MVP tidak menjadi bypass untuk mengubah transaksi bisnis tenant.
- Resource lintas tenant sebaiknya menghasilkan not-found yang aman, tanpa mengungkap keberadaan atau isi record. Aktor dengan role yang salah menerima penolakan akses.

### Validasi, transaksi, dan respons

- Semua mutasi memvalidasi input di backend melalui request/action validation dan policy. Input hanya memuat data yang boleh diubah oleh aksi tersebut; jangan mass-assign seluruh model.
- Tanggal bisnis berupa tanggal kalender di zona `Asia/Jakarta`; waktu kejadian disimpan sebagai instant UTC dan ditampilkan kembali sesuai zona operasional. Rentang kamar memakai `[start_date, end_date)` dan menolak rentang kosong/terbalik.
- Nominal dalam Rupiah berupa bilangan bulat positif/non-negatif sesuai field; seluruh perhitungan, alokasi, saldo, dan pembulatan dijalankan backend, bukan dipercaya dari UI.
- Tarif katalog menjadi nilai awal harga: tarif khusus kamar meng-override tarif tipe kamar bila keduanya berlaku pada tanggal yang sama; jika tidak ada tarif khusus, gunakan tarif tipe. Preview availability dan form booking/check-in memakai resolver server yang sama; saat menyimpan, backend resolve ulang nilai awal dengan aturan itu, tetapi tetap mengizinkan harga kesepakatan yang pemilik sesuaikan. Validasi nominal harga lalu simpan harga kesepakatan aktual sebagai snapshot pada booking/tenancy/perpanjangan, tanpa mensyaratkan nilainya sama dengan katalog dan tanpa menulis ulang snapshot saat katalog berubah.
- Perubahan yang dapat menambah atau mengubah pemblokir availability menjalankan transaksi dengan urutan lock stabil: row properti tenant-owned sebagai mutex bersama, lalu row kamar terkait menurut ID, lalu record booking/tenancy/maintenance menurut ID. Baca ulang status dan periode setelah lock, cek ulang overlap, lalu commit seluruh perubahan atau rollback. Archive properti memakai lock properti yang sama dan memeriksa ulang pemblokir di dalam transaksi. Semua aksi booking, check-in, tenancy, maintenance, serta perubahan status properti/kamar yang dapat menambah atau melepas pemblokir wajib mengikuti urutan lock ini agar archive dan availability tidak berlomba.
- Pembayaran, alokasi kas, perubahan liability, settlement deposit, refund, dan pengeluaran yang saling terkait harus atomik. Request ulang tidak boleh menggandakan cash event atau movement; koreksi memakai reversal/adjustment dengan audit, bukan menghapus histori.
- `GET` mengembalikan halaman/props Inertia atau file export. Mutasi sukses mengembalikan redirect Inertia ke halaman hasil dengan flash message. Untuk validasi field, redirect kembali ke form dan flash error ke session agar Laravel/Inertia membagikannya melalui `page.props.errors`; Inertia tidak menerima respons `422` untuk pola validasi form ini ([rujukan Inertia](https://inertiajs.com/docs/v3/the-basics/validation)). Hindari respons JSON pada alur UI MVP.
- Keadaan overlap atau saldo yang berubah sejak halaman dibuka ditangani sebagai kegagalan aksi yang dapat dipulihkan: rollback transaksi, redirect kembali dengan error bag/flash yang menjelaskan konflik, dan tampilkan ringkasan data terbaru. Pengecualian expiry: jika check-in atau perpanjangan grace menemukan booking confirmed sudah kedaluwarsa, commit transisi rekonsiliasi ke `NO_SHOW` dan audit lebih dahulu, lalu redirect dengan konflik; jangan rollback transisi expiry. Jangan memakai respons `422` JSON atau `409` untuk konflik bisnis pada alur form Inertia. Sesi/CSRF mengikuti penanganan Laravel; akses ditolak secara aman (403 atau 404 sesuai kebijakan penyamaran).
- Props halaman hanya menyertakan kolom yang diperlukan aktor. Jangan mengirim nomor KTP/identitas resmi karena data itu tidak dikumpulkan. Export menerapkan scope dan filter tenant yang sama dengan halaman laporan.

### Bentuk UI dan aksi

- Action yang membuat/menampilkan form mengembalikan page component Inertia, misalnya `Owner/Bookings/Index` atau `Platform/Owners/Show`.
- Aksi `POST`/`PUT` di bawah adalah endpoint command. Pisahkan perubahan bisnis penting: confirm/cancel booking, check-in, checkout, extend, archive, approve settlement, dan record refund.
- Daftar dan detail memakai pagination/filter server-side bila sesuai; filter hanya mempersempit data dalam scope aktor.
- Rujukan kualitas memakai ID acceptance atau nama bagian yang sama persis dengan heading [Strategi Kualitas](../quality/testing.md). `ACCESS-01/02`, `PRIVACY-01`, dan `PRICE-01/02/03` didefinisikan di sana; istilah area seperti “Ketersediaan dan booking”, “Masa sewa”, “Keuangan”, dan “Maintenance dan laporan” merujuk ke heading tersebut.

## Ketertelusuran implementasi

Sebelum route ditulis, setiap baris tabel di sini harus punya controller/action, Form Request atau validator ekuivalen, policy, query tenant-scoped, hasil Inertia yang dibutuhkan UX, serta feature test sesuai acceptance reference. Detail field/relasi mengikuti [Skema Relasional](../data/relational-schema.md); aturan tumpang tindih mengikuti [Ketersediaan Kamar](../business/availability.md), transisi tenancy/booking mengikuti [Booking dan Masa Sewa](../business/booking-tenancy.md), dan hasil uang mengikuti [Keuangan dan Laporan](../business/finance.md). Jika kontrak route membutuhkan perilaku baru yang tidak ada di canonical business rules, catat di [Keputusan Wawancara](../decisions/open-questions.md) sebelum mengimplementasikannya.
