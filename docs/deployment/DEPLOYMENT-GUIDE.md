## 1. Gerbang menuju produksi

1. **Verifikasi read-only.** Cocokkan node PVE, ID/hostname/IP LXC, user/service runner, workspace dan labels GitHub dengan host yang benar; periksa runtime, service, port, disk/inode, RAM, CPU, storage, hak akses dan versi. Periksa nilai efektif konfigurasi tanpa mencetak rahasia. Cocokkan Cloudflare Tunnel, router Traefik dan target aplikasi. Simpan waktu, sumber dan mismatch; label runner saja bukan bukti identitas.
2. **Verifikasi kandidat terisolasi.** Jalankan lint dan test, acceptance PostgreSQL pada database uji terpisah, serta uji build, migrasi dan health untuk commit kandidat. Periksa hasil simulasi kegagalan dan rollback; jangan gunakan database produksi untuk test atau `migrate:fresh`.
3. **Siapkan keamanan data.** Buktikan backup database dan file privat tersimpan di luar node dan telah direstore pada lingkungan uji. Pastikan APP_KEY lama tersimpan aman dan stabil. Tinjau kompatibilitas setiap migrasi dengan release lama dan baru serta rencana pemulihan; jangan gunakan rollback database otomatis.
4. **Siapkan impact assessment dan persetujuan terpisah.** Catat perubahan layanan/ingress, risiko dan downtime, kapasitas, kandidat SHA dan versi sebelumnya, urutan migrasi/aktivasi, indikator sukses dan kegagalan, serta prosedur rollback dan kontak operator. Peroleh persetujuan eksplisit sebelum mengubah sistem live.
5. **Aktivasi dan verifikasi.** Hanya setelah gerbang di atas terpenuhi dan disetujui, jalankan prosedur yang telah ditinjau untuk commit tersebut. Verifikasi versi aktif, app/web, database, asset, scheduler, queue bila dipakai, log tersanitasi, dan jalur ingress. Catat hasil serta status aktual pada inventaris. Kegagalan tidak berarti database boleh di-rollback secara otomatis.

Gerbang tetap **BLOCKED** jika bukti tidak tersedia, termasuk ketika implementasi repository telah lulus pengujian lokal. Jangan install, restart, mengubah konfigurasi atau menjalankan deployment/migrasi produksi untuk mengisi kekosongan audit.

## 3. Konfigurasi repository dan kontrak runtime

Repository sudah memiliki [Dockerfile](../../Dockerfile), [compose.yaml](../../compose.yaml), [.dockerignore](../../.dockerignore), dan [workflow deployment](../../.github/workflows/deploy.yml). Keberadaannya tidak membuktikan instalasi Docker, runner, image, layanan, atau deployment pada LXC. Baca implementasi yang telah ditinjau pada commit kandidat sebelum menggunakannya; rencana implementasi dan status uji dapat berubah.

Image runtime harus memuat dependency produksi dan asset yang dibangun dari lockfile; pengujian harus membuktikan manifest Vite sesuai asset yang disajikan. Pertahankan PostgreSQL dan `storage/app/private` dalam storage persisten, dan batasi akses sesuai user runtime. PostgreSQL tidak dipublikasikan ke LAN/internet. Scheduler yang dikonfigurasi perlu diverifikasi proses dan hasil pekerjaannya; worker queue hanya dibutuhkan jika ada pekerjaan asynchronous yang benar-benar digunakan, dengan release yang sama seperti aplikasi.

Workflow lokal dipicu hanya setelah workflow `tests` (ID remote `405373892`) sukses untuk push `main` dari repository yang sama. Ia mengikat checkout kandidat ke SHA tersebut dan memeriksa SHA head `main` lagi sebelum aktivasi. Tidak ada `workflow_dispatch`; concurrency target memakai satu group, antrean `queue: max`, dan `cancel-in-progress: false`. Repository variable `KOSTKITA_DEPLOYMENT_ENABLED` harus bernilai `true`; tanpa setelan itu, job deployment dilewati. Job juga memerlukan `KOSTKITA_EXPECTED_HOSTNAME`, `KOSTKITA_MIN_FREE_DISK_BYTES`, dan `KOSTKITA_MIN_FREE_INODES`; dua ambang kapasitas harus berasal dari pengukuran LXC, bukan tebakan. Sebelum membuka flag, pemilik repository harus menonaktifkan workflow legacy, melindungi `main` dengan required checks, lalu membuat GitHub environment `production`, menambahkan required reviewers, dan membatasi deployment branch ke `main`. Setting remote ini belum diverifikasi atau dikonfigurasi.

Runner harus bernama `kost-kita`, berada pada Linux x64 LXC, hostname harus sama dengan `KOSTKITA_EXPECTED_HOSTNAME`, dan host harus memiliki `192.168.0.26`. Skrip juga mendeteksi virtualisasi LXC dan mengikat source ke SHA commit. Pemeriksaan itu tidak membuktikan Proxmox node atau CT ID; cocokkan out-of-band di Proxmox sebelum menetapkan variable/flag. Source kandidat dibangun dari arsip commit di runner LXC; release dan file lock `/opt/kostkita/deploy.lock` disimpan di host, lock memakai `flock` (kernel melepas lock saat proses berakhir), file env dibaca dari `/opt/kostkita/.env`, dan tidak ada push ke GHCR. Folder deployment/runtime belum diperiksa langsung.

Sebelum aktivasi, skrip memastikan database, Compose project, release image lama, dan named storage volume yang ada dapat dipakai untuk pemulihan. File env harus reguler (bukan symlink), dimiliki runner, dan bermode `0600`. Kandidat menjalankan preflight config efektif yang mensyaratkan `APP_ENV=production`, `APP_DEBUG=false`, HTTPS `APP_URL` KostKita, `APP_KEY` valid untuk `APP_CIPHER`, PostgreSQL pada host `db:5432` tanpa `DB_URL` override, dan secure session cookie; output hanya menyebut nama setting yang gagal. Pemeriksaan ini belum membuktikan `.env` live karena akses LXC tidak tersedia. Ia memeriksa direktori Laravel sebagai `www-data`; migration pending pada image aktif maupun kandidat menghentikan proses tanpa menjalankan migration otomatis. `migrate:status` memeriksa nama, bukan checksum isi file. Backup/restore evidence juga belum memiliki gerbang otomatis, sehingga pemilik harus memverifikasi dan mencatat buktinya secara terpisah sebelum aktivasi. App dan scheduler pada Compose kandidat berjalan sebagai `www-data`; entrypoint menolak directory yang tidak ada/tidak writable dan tidak mengubah permission file persisten secara rekursif. Jika volume lama tidak kompatibel, hentikan deployment dan rencanakan perbaikan permission terpisah setelah owner/mode serta cakupan file ditinjau.

Simpan file rahasia runtime di luar build context/source, dengan owner terbatas dan mode yang sesuai; jangan cetak isinya atau mengirimkannya ke log, artifact atau image. Periksa keberadaan file env lain yang dapat mengesampingkan konfigurasi produksi tanpa memaparkan nilainya. `APP_ENV=production`, `APP_DEBUG=false`, URL HTTPS, koneksi PostgreSQL dan cookie aman harus diverifikasi pada kandidat. `APP_KEY` stabil antar-release; jangan generate ulang saat deployment. Role aplikasi database harus terbatas dan terpisah dari role bootstrap. Konfigurasi email sungguhan diperlukan sebelum fitur verifikasi email/reset password dibuka ke publik.

Proxy Laravel saat ini dikonfigurasi di [bootstrap/app.php](../../bootstrap/app.php); nginx meneruskan request ke PHP-FPM. Uji `REMOTE_ADDR`, `X-Forwarded-*`, HTTPS, host dan IP klien melalui jalur yang sebenarnya sebelum menganggap daftar trusted proxy sudah tepat. Jangan mengubah konfigurasi hanya berdasarkan asumsi topologi.

## 4. Operasi dan pemulihan

Simpan identitas commit, image/release, dan konfigurasi yang diperlukan untuk mengidentifikasi versi aktif dan versi sebelumnya. Skrip lokal mempertahankan image sebelumnya dan mencoba memulihkan image app/web/scheduler di atas Compose file kandidat bila verifikasi sesudah aktivasi gagal. Ini rollback image-only; file konfigurasi Compose sebelumnya tidak dipulihkan otomatis. Image, volume dan database tidak di-prune atau dihapus, dan tidak ada migrasi otomatis. Kegagalan rollback tetap memerlukan operator. Uji rollback aplikasi dan traffic pada data uji setelah kompatibilitas schema diverifikasi; aktivasi beberapa container tidak otomatis atomik sehingga jendela gangguan dan kegagalan parsial harus dibuktikan pada rehearsal.

Monitor ruang disk, inode, memori dan waktu build karena build dan layanan berbagi LXC. Tinjau cache/log dan permission storage, kesehatan database, jadwal dan worker bila dipakai setelah setiap release. Hindari pembersihan global image/volume yang belum dipetakan; jangan menjalankan `docker compose down -v` terhadap stack berisi data.

Periksa ingress aktif di dashboard Cloudflare dan file provider Traefik, lalu uji HTTPS, login, aset dan cookie dari jalur publik. Jangan memublikasikan database, SSH, Proxmox Web UI atau dashboard Traefik. Simpan data sensitif, backup dan log hanya pada lokasi yang aksesnya dibatasi.
